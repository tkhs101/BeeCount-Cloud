## 上一轮我说「防线 4 测不到」—— 那个结论下得太早

上轮我把 \`if getattr(claimed, "rowcount", 0) != 1:\` 改成 \`if False:\`,
测试全绿,查源码发现**防线 2 排在防线 4 之前**,于是写了条测试把这个
事实钉住,并写「真要验它得上两个真连接 + 显式交错」。

**但「顺序调用测不到」不等于「测不到」。** 顺序法确实造不出那个状态,
换**重入**就能:

\`\`\`
防线 2(last_period == pkey?)  ->  防线 1(compute_statement)
  ->  payable  ->  防线 4(条件 UPDATE)  ->  self_call
\`\`\`

把 \`compute_statement\` 包一层,在**它里面**把另一个 session 的
\`repay_one\` 整个跑完:

- A 过了防线 2(此刻 \`last_period\` 还是 None)
- A 调 \`compute_statement\` -> 里面完整跑 B -> B 拿锁、**提交**、写完交易
- A 回到主线,拿着**过期的**余额去抢锁
  -> \`WHERE last_period IS NOT '2026-11'\` 匹配 0 行 -> \`skipped_locked\`

这就是多 worker 抢同一期时的真实路径。

**两个独立 session 是必需的** —— \`StaticPool\` 的内存库所有 session
共用一个连接,未提交事务对另一个「看得见」,造不出竞态。所以这条用
**文件库 + 两个引擎**。
